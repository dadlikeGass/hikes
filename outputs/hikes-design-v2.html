01

定位与初心

从前两版稿子里抽取出来的同一件事

前两版各自留下什么

山径 Trailbook（trail-ui.html）：路线资料库。“每一条山径，都有一本鲜活的路书”， 核心是搜索、难度、分段路书、路况核验、共建认领。它的价值是信任——让一个陌生地方变得敢去， 也让人愿意把走过的地方整理成别人用得上的东西。

山里见（social-ui-plan.md）：扫码到访与连接。“山里，总有人与你同频”， 核心是扫码、到访卡、留言墙、留给下一位、山径拼图。它的价值是温度—— 让一个人在山上不孤单，也让走过的路留下痕迹。

两者不是两个产品，是同一条链的两端：路书让人敢去，到访让人留下，留言让下一个人不孤单。 前两版的问题是它们各自成了完整的首页，谁也没接住谁——Trailbook 把"去过的人"做成了静态数据， 山里见把"路书"降级成了详情页的附属信息。

定位（已确认）

给每一个岔路口一个路书，
给每一个山峰一个打卡点。

这句话同时定义了产品的内容供给和交付形态：
岔路口 = 路书点，解决"往哪走"，靠用户共建（拍来向视角、指方向）；
山峰 = 打卡点，解决"我来过"，靠到访产生内容（第 N 位、到访卡、用时榜）。
两类点位的字段、页面形态与后台管理都要分开。

03

首页布局

首屏三块 · 完整七块 · 按优先级排
  1. 1

    问候 + 山况一行

    回答"现在去不去得了"。天气、日落时间、路况摘要占一行，不占屏。 这是唯一一处"环境信息"，它把"打开 app"变成"要不要出门"。

  2. 2

    今日主卡（首页唯一主角，三态切换）

    没想好去哪 → 推荐一条路 + 双按钮；在路上 → 换成钴蓝的行进卡；刚结束 → 换成到访卡预览。 首页的心脏不是信息流，是"我现在该做什么"。

  3. 3

    足迹三格：想去 / 到过 / 拼图

    把原方案的"想来 + 拼图 + 到访"压成一行三格，点进「我」。 进度感要一直可见，但不能各占一块屏。

  4. 4

    今天有人在山里（动态流）

    每张卡必须带地点与时间，点地点进"地点空间"。默认只放 2–3 张 + 更多。 和晒图社区的区别：动态挂在地点上，而不是挂在人身上。

  5. 5

    今日登顶用时榜

    默认展示三行：第 1 名、第 2 名、我（高亮）。点进地点看今日 / 好友 / 我的纪录三个视角。 这是最强的"想再回来一次"的钩子——名次会变。

  6. 6

    留给下一位（信封卡）

    淡紫信纸 + 手写一句话 + 现场拆开。保留原方案里最有情绪的一件东西。 它同时承担"解释玩法"和"制造向往"两件事。

  7. 7

    底部导航，中间扫一扫凸起

    出发 / 山径 / 扫一扫 / 消息 / 我。出发与山径分开，把资料库还给用户。 "想去 + 路书"不再挤在同一格，找山和上山各有入口。

扫码落地页与回访

一个二维码 = 一个点位 = 一个稳定子页面

二维码与落地页

印刷标牌（短链）→302 跳转→ 点位子页面 H5→打卡 / 路书

二维码里印的是短链（如 hikes.app/p/QSD1024），不是页面真实地址。 标牌贴上去就收不回来，短链可以让页面结构以后随便改而不用重印。

服务端按 UA 分流：手机 → 点位子页面；桌面 → "用手机扫码"页 + 二维码图 + 输入点位编号。 子页面必须免登录可玩（昵称即可打卡），登录放到后面，否则微信里第一步就流失。

标牌上同时印：点位名 · 点位编号 · 一句话引导 · 短链文字。编号要能在扫码失败时手动输入。

微信 / 其他扫码工具能不能跳进来

能。微信扫码打开的是内置浏览器，普通 https 网页可以直接打开—— 这正是"网页版优先"的价值：不需要小程序也能完成打卡。

但要绕开四个坑：
1. 域名必须国内可访问、已备案。未备案域名在微信里会被拦成"无法打开网页"。
2. 不要用 deep link（如 hikes://）做二维码内容。没装 App 的人只会看到空白页。
3. 不要做诱导分享或强制下载。微信对这类外链拦截很严，"分享三个群解锁"这种玩法不要碰。
4. 页面内不要再放一个"扫一扫"。用户已经在扫码了；真要调微信相机需 JS-SDK + 公众号配置， 成本高收益低，直接降级成"输入点位编号"更稳。

系统相机（iOS / 安卓原生）、支付宝、抖音识别 https 链接后都会跳系统浏览器， 所以落地页要在无 cookie、无登录、弱网下都能渲染出打卡按钮。

除了扫码，用户为什么要回来

关系型（最强）　有人回应了你的留言 / 击掌 / 合影请求被接受 / 关注的山友又上山了 → 消息红点
延迟回报型（第二强）　写给未来自己的信按日期解锁 / 你留给下一位的那句话被谁拆开了 → 推送
竞争型　用时榜名次被超过 / 个人纪录被刷新 / 今日榜换了人
进度型　山径拼图 3/6 · 想去清单 · "第 5 个点位"这类累计
内容型　收藏的地点有新的路况核验、新的留言、新的到访者
被动召回　分享出去的到访卡被人击掌 / 被留言，通知把人拉回来

排序就是优先级：消息红点 > 未来信解锁 > 用时榜名次 > 拼图进度。 首页之所以把用时榜放在信封卡上面，就是为了让"回来一次"的理由在第一屏之后马上出现。

07

设计判断与待确认项

这一版我改了什么、为什么，以及我不确定的地方

我做的四个判断

1. 首页主角从"动态流"换成"今日主卡"。
原方案首页第一屏是扫码按钮 + 山友动态，等于默认用户已经在山里。 但大部分打开时刻是"我想出去走走"。主卡三态把出发前、在路上、刚结束这三种状态统一成一张卡， 扫码降级为主卡里的一个按钮，而不是整个首页的假设。

2. 导航把"想来"换成"山径"。
"想去"是一个状态列表，不是目的地，撑不起一个 tab； 而 Trailbook 那套搜索、难度筛选、分段路书、共建认领才是 hikes 的信任基础， 它需要自己的入口。想去/到过变成地点上的状态，同时收进「我」。

3. 动态挂在地点上，不挂在人上。
每条动态卡必须带地点和时间，可点进"地点空间"。 这决定了产品的形状：主角是山径，不是博主。

4. 扫一扫是动作，不是内容，所以它不占 tab。
四个功能 tab 回答四个问题（出发 / 山径 / 消息 / 我）， 扫一扫回答的是"现在做什么"。它做成底部正中凸起的钴蓝按钮，是全站唯一一个实心饱和色的常驻控件。

我要提醒的两件事

用时榜保留，改掉的是那句文案。榜单留下，冲突的「慢一点也没关系，风景会等你」删掉； 同时在榜单旁加一句安全提示，并给每个人一条"跟自己比"的纪录线。 这样榜单的动机是"我想再快一点"，而不是"我比别人慢"。
扫码是入口，但不能是唯一入口。没有到现场的用户打开 app 时， 扫码按钮是无效的。所以「我已经到了 · 扫一扫」永远和「看看这条路」并列出现， 让两种状态的人都有下一步。

已经定下来的

定位：给每一个岔路口一个路书，给每一个山峰一个打卡点。
品牌语改掉了：原副线「慢一点也没关系，风景会等你」与用时榜直接冲突，已换成 「上面风大，记得带件外套。」——只讲关心，不讲快慢。主品牌语为「每一次上山，都算数。」
用时榜保留并前置：首页第三屏，用三行结构（第 1 名 / 第 2 名 / 我）。三条底线—— 只对山峰类点位生效、同屏给"比上次快多少"的个人纪录线、旁边一句安全提示。榜单靠"名次会变"制造回访， 不靠羞辱慢的人。

新增的待确认

① 用时榜的对比范围：全站今日榜 / 仅好友榜 / 只跟自己比？这决定伤害感和回访强度，三种的伤害感递增顺序是好友 < 全站 < 只跟自己比。
② 点位分型是否用两套落地页模板：岔路口（路书点）以"往哪走"为主，山峰（打卡点）以"我来过"为主。我按两套设计的，但命名要定。
