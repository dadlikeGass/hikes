## 一、目标与范围

### 产品定位

以山峰、岔路和路段为社区单元，通过现场二维码连接徒步、登山、越野人群与当地维护人。完整线路服务行程理解；三类留言板积累地点内容；山大王承担山脚／山顶布点和论坛维护，是核心供给角色。

完整线路只呈现轨迹、长度、累计爬升和平均用时等行程基础信息；难度及登顶用时属于有明确起终点、方向的单段线路。一个山头对应一个独立山顶留言板，同山不同路线共享它。

### 北极星

1.0 不是"做完产品"，是**验证三件事**：

1. 用户会不会**扫码**（实体标牌前）
2. 用户会不会**留言**（到了之后有没有话想说）
3. 用户会不会**反复打开**

一切取舍以"能不能拿到这三个数据"为准。

### 范围

| 保留（1.0） | 延后 |
| --- | --- |
| 扫码识别点位、打卡、第 N 位 | 照片上传（OSS/签名/审核，工程量最大且不验证假设） |
| 文字留言 + 赞 / 踩 | 站内信、好友、求合影、组队 |
| 路书（列表 / 详情 / 分段着色 / 山顶） | 活动报名 |
| 岔路情报 + 核验 | 消息中心 |
| 用时榜、山径拼图、我的 record | 真实地图（先用 SVG） |
| 我去过的地方、未来信 | 小程序（W6 再上） |
| 首页、维护台 | |

### 三端节奏

- **H5 先行**（W1–W5），微信里直接打开，香港节点免备案
- **维护台**（W5）桌面 Web，内部使用
- **小程序**（W6 后）看回访数据再决定，用 Taro 复用 80% 逻辑

## 四、功能设计（逐页）

### 首页
品牌条（居中，左上角可点回首页）→ 扫码窄条 → 热门线路轮播卡 → 周末组队活动卡 → 照片瀑布流。

品牌条：中文「到此一游」，下面一行英文 **For all hikers**（不是 HIKERS）。
扫码窄条文案：**「扫码，{昵称}到此一游」**——昵称取当前用户（`H.me.name`），未登录时兜底。

轮播卡：优先完整线路轨迹、线路名、长度、累计爬升、平均用时与收藏；仅估算时写「参考用时」。完整线路不赋单一难度，登顶难度／用时进入具体路段后展示。旧卡上的全线难度徽标、最快登顶与记录保持者不再作为完整线路摘要要求。
**轮播 5 秒自动播放，用户手动滑动后停止。**

### 路书
完整线路列表先展示轨迹、长度、累计爬升、平均／参考用时。路段详情提供路况描述入口，落到共享的路段留言板。难度筛选只适用于明确的单段线路，不将完整线路包装成单一难度。

登顶用时仅在同一起终点、路径和方向的路段内比较；同山不同上山路线不混排。

### 线路详情
完整线路轨迹 → 名称 + 长度／累计爬升／平均用时 → 关联山峰与有方向的路段 → 各路段情况及留言入口。分段图、剖面可解释路线；难度判定卡归具体路段，不作为整条线路评级。路书中的路段留言与该路段独立板共享内容。

### 关于难度

完整线路用于理解整体行程，只呈现基础数据，不给整线单一难度等级。单段线路有明确起终点、方向与路径，才进行难度定义和登顶用时记录。

管线的爬升／坡度分级是候选判断，维护核验及路况描述补充技术动作、通行变化等信息；自动分级不能等同于安全保证。算法分段与可复用的登顶路段需明确关联。单段难度仍沿用形状＋颜色，hidden 仅人工设定。

山头页展示从不同入口上山的各路段，不能给山峰套一个脱离路径的用时或难度。具体阈值与跨算法版本兼容策略需在接口改造前补齐。

顶部先放**占山为王入口卡**：橙红渐变整卡 + 山脊剪影 + 巡山小妖（举「巡山」令旗，气泡「大王叫我来巡山」）。

| 左·第一行 | 做一个游戏人间的山大王～ | 细体小字 11.5px / 300 |
| 左·第二行 | 为你热爱的山峰做一个更大的留言板 | 同上 |

## 【核心模型】山头独立于线路，一个山头对应一个山顶留言板

**山头是独立地理对象。** 三峰连穿等完整线路按顺序引用山峰和路段；同一山头可被多条线路经过，仍共享一块山顶板。山脚到山顶的不同路段分别定义难度和用时。二维码挂在具体点位，点位关联山峰、岔路或路段上下文。

> 旧定义「最难爬升段所通向的顶 = 山头」已废弃；它最多用于选择线路推荐峰。管线自动识别候选峰与路段并联网检索名称，再匹配已有对象、核验和发布，不能每条轨迹都复制一个山头。

于是每个山头有自己的**点位和编号**（`SF-01` / `DLS-02` …）——这才谈得上"给每一个山峰一个打卡点"：
没有点位就没有编号、没有二维码、扫码扫不到、留言没地方挂、拼图也无从点亮。

| 卡片位置 | 内容 | 规矩 |
| --- | --- | --- |
| 大字标题 | 山峰真名 | 采不到就写 **「名称待定」**。**绝不许拿线路名冒充峰名** |
| 第二行 | 海拔 + 地点；选定上山路段后显示该段数据 | 必须标注入口和方向 |
| 小字注释 | **@三峰连穿 · 看整条路书 ›** | 可点，跳这条线路的路书 |
| 右侧 | 登顶最快用时 / 记录保持 | |

**热门登顶榜同理**：一行就是一个山头（主峰），不是一条线路。

历史实现待迁移：`seeds/backfill_peak_points.py` 给每条线路的每个顶 + 山脚补出点位
（`SF-S` 山脚、`SF-01` 第 1 个顶…），各自带编号和二维码。可重复执行。

**热门登顶榜**（在山头列表下方，替换了原来的「最近有人去过」）：
一座山一张卡，按「**本周打卡热度 + 用户关注度**」排，按稳定山峰身份聚合；自动来源与自建来源先去重，不能按完整线路复制山头。**只列前 5 座**。旧实现的线路级热度需迁移，统计去重口径另行落实。

卡片排版固定为——

| 位置 | 内容 |
| --- | --- |
| 左·大字 | 独立山峰名 + 地点 |
| 左·下面 | 单段爬升 · 单段距离 · 打卡人数 |
| 右 | 登顶最快用时 / 记录保持 |
| 名次 | 左上角方块，前三名橙色 |

右侧按钮 **「所有」** 打开弹层，里面三块：① 打卡人数最多的 5 座主峰（同样的卡）
② 最近一周的打卡流水（谁 · 哪座山 · 多久前 · 用时）③ 底部「查看更多」。

「单段爬升 / 单段距离 / 登顶用时」属于明确的上山路段，展示时同时标明入口和方向；不得将某条完整线路最难段的数据冒充该山的统一属性。

```text
score = 本周打卡 × 3 + 近 30 天打卡 + 关注 × 2
```

本周权重最高——榜要反映"现在热不热"，不是"历史上攒了多少"。**口径必须印在榜下面**，
否则用户会以为它跟上面那个海拔榜是一回事。
关注度来自 `wants` 表（不是 localStorage）——只在浏览器里点，服务端永远算不出热度。

演示热度（真实扫码进来前榜全是 0，没法验收 UI）：
`docker compose exec api python /srv/seeds/seed_heat_demo.py`，清掉加 `--clear`。

点位确认发布后给二维码，并**明确现场布设任务**：① 打印物料 ② 在获准的山脚 / 岔路口 / 山顶位置按合适形式布设
③ 有人扫码才长内容，「没人扫，这个点位就一直是空的」。之后才是试用期考核进度。

**表单底部两个按钮**（不是"提交/取消"，是两条不同的路）——
主按钮那句跟着入口走：从山头进来是「成为山大王」，从岔路进来是「成为NPC指路人」：

| 按钮 | 小字注释 | 干什么 |
| --- | --- | --- |
| 成为山大王 | 让大家扫码打卡 | 自己开一座山：填信息 + 传 GPX → 拿编号和二维码 → 贴出去让人扫 |
| 成为NPC指路人 | 给后来的人指路 | 同一件事，但建的是**岔路点位**（`kind=junction`）：把"往哪走、能不能过"写成情报 |
| 成为版主 | 建立留言板 | **不新建、不发二维码**，接管一个已经立好的山头的**线上留言板** |

「成为版主」打开的是可认领点位列表——**按稳定山峰身份去重，一座山一行**（名称相同或同属一条线路不能作为合并依据），
每行右侧「我来维护」，点进去才是认领表单（昵称 + 联系方式）。

**版主和山大王是两回事，别再混：**

| | 山大王 | 版主 |
| --- | --- | --- |

山顶大图 → 海拔 + 关联完整线路 + 近 30 天到访 → 不同登顶路段的难度与用时 → 山顶留言板 → 底部「收藏到想去 / 我也到了」。照片墙属于后续范围。

### 岔路页（路书点）
搜索栏之上放**同一张入口卡的岔路版**：主标题「我是NPC指路人」，其余排版与山头页一致
（同一条卡、两套文案，跟着分段换）。岔路页首图上那颗按钮也从「占山为王」改成「当NPC指路人」。

来向视角大图 → 编号 + 属于哪条线路 + 第几个点位 → **「你在这里 · 往哪走」**（照片 + 箭头 + 一句话 + 下一段距离爬升）
→ **岔路情报卡流**（已核验 / 待核验 + 确认人数）→ 上报一条情报 → 顺路打卡（次要按钮）。

**岔路是情报，山头是情绪。** 两类点位两套页面，不合并。

### 三类留言板与维护人广告

山顶板承载到访纪念和交流；岔路板承载来向／去向与现场情报；路段板承载有方向、位置、观察时间的路况描述。完整线路不新增第四类板。

**每个留言板一个广告位**，由维护人上传、系统审核，默认在第一屏之外；优质广告可由系统提升至第一屏。废弃按维护等级增加单板广告位数量的规则。审核、授权与利益冲突细则见 PERMISSIONS.md（提案）。

### 到达页
`#N` 印章 → 「你到了，山友」→ 留下到访卡 → 三小格（首次 / 用时 / 拼图 +1）→ 用时榜一行 → 拆信 → 留言板 → 折叠趣味区。
**扫码后 3 秒内必须能完成打卡**，凡是需要读和决定的全部往后放。

### 消息
互动 / 请求 / 信件 / 系统 四组。每条带**地点上下文胶囊**，点击回到现场而不是某人的主页。

### 我
头像 → 山径拼图 → **我的 record**（爬过的山峰 + 登顶时间）→ 我去过的地方（地图/拼图/列表）→ 想去 → 我的山头 → 山间信箱 → 发起活动。

**山径拼图（规则写死）——一格是一座山：**

- **一格 = 一座山**（北京结、萝芭地北尖…）。**山脚不单独占格子。**
- 一格里有**两个扫码输入点**：**山脚** + **山顶**，各自扫码各自点亮。
- 格子上记三个维度：**打卡人 / 打卡时间 / 打卡次数**。
- 只扫了其中一个 → 点亮，没有时间。
  **两个都扫了 → 格子里是这次登顶用时**（山顶那次 − 同一天山脚那次）。
- 没扫过的格子灰着——一眼看出这条线上哪几座山还没上。
- **点一格**看这一座山的每一次记录（谁、什么时候、用时多少），
  以及两个扫码点各自的编号和去过几次；再点进它的留言板。

一天里爬两个顶，两个格各算各的用时。顺序：有完整记录的排前面。

数据源 `GET /api/me/route-progress`。
~~"到过 N 个点位就点亮 N 格"~~ 已废弃：格子不对应任何点位，点也点不开。

### 维护台（桌面）
点位台账（我维护的 / 待处理 / 未认领）→ 单点位管理：二维码（编号 + 短链 + 预览 + 重新生成）、标牌预览、子页面内容、**难度判定**（单段爬升比 + 地形方式）、动态内容核验、发布与版本记录。

**二维码里印短链，不印页面地址。** 编号一旦发布即锁定，页面内容随时可改。

## 六、数据表（PostgreSQL 15 + PostGIS 3）

### users
| 字段 | 类型 | 说明 |

| id | bigserial PK | |

### points（点位，打卡点 + 路书点 + 起点）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigserial PK | |
| code | text UNIQUE | **生成后不可变**，二维码里印的就是它 |
| type | text | `peak` / `junction` / `trailhead` |
| name / route_id / index_in_route | | |
| level | text | `easy/mid/hard/hidden`，hidden 仅人工 |
| altitude | int | 仅山峰 |
| geom | geometry(Point,4326) | 空间索引 |
| guide | jsonb | 往哪走：箭头 / 标题 / 说明 / 下一段 |
| maintainer_id | bigint → users | 认领人 |

### routes / route_segments / route_peaks
| 表 | 关键字段 |
| --- | --- |
| routes | id, name, sub, km, up, down, level, `geom geometry(LineString,4326)`, `path jsonb`（归一化坐标，喂前端 SVG）, `profile jsonb` |
| route_segments | route_id, no, from_km, to_km, km, rise, pct, level, kind(climb/desc/flat), `source`(auto/manual), `confirmed`, `geom` |
| route_peaks | route_id, index, km, altitude, rise |

**`up` / `down` 必须用原始高程 + 3 m 滞回计算**，不能用平滑后的高程（已踩坑）。

| --- | --- |

### comments / comment_votes
| 表 | 关键字段 |
