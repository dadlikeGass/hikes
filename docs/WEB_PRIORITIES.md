# 网页调整与首条验收路径

> 2026-10-13 用户确认。本文覆盖 PLAN.md 中冲突的页面模块、入口顺序与旧周排期；描述目标行为，不表示代码已实现。

## 目标与顺序

让山友愿意参与，让维护人愿意建设。统一文档、稳定地点模型、游客注册闭环是开发地基；首条交付路径是山顶扫码落地页 → 独立山头页 → 维护人招募与维护台，通过后扩展岔路与路段。

## 七项页面要求

1. 首页顺序为扫码入口、完整线路卡、近期留言与路况、维护人招募。线路卡展示轨迹、长度、累计爬升、平均／参考用时，不展示全线单一难度或登顶纪录。近期内容分别取自山顶感受、岔路更新、路段描述，保留地点、观察时间及原板入口；无内容显示空态，不编造留言。未上线的组队、未来信、照片流不占位置。
2. 山头页先展示山名、海拔、到访与纪念入口，再展示各登顶路段的难度和用时、山顶留言及维护人。岔路页先展示来向、去向及最近核验信息，再展示情报、纠错、NPC 指路人。路段页先展示起终点、方向、长度、爬升及难度，再展示路况、个人用时、留言及维护人。同山一块山顶板；路书引用同一块路段板。
3. 保留“占山为王”的吸引力。巡山小妖用于山头招募、维护任务、贡献反馈；NPC 指路人用于岔路说明、信息核验、指路人招募。角色资产需透明背景、简化细节，并验证小尺寸辨识度，不将整张设定图缩入卡片。普通浏览小巧展示，明确招募才使用大卡。
4. 山顶扫码顺序为认出地点 → 我到了 → 到访凭证 → 可选保存账号、留一句话、看留言。岔路扫码先指路，再顺路打卡。主动保存到账号、公开留言、关注时才注册。私人纪念与公开留言分开，注册完成回到原位置并保留记录、草稿。
5. “我”页顺序为我的山峰记录、本次及历史纪念、想去的地方、我的贡献、我维护的留言板。体现首次、重复到访与帮助后来者；个人用时保留但不以最快纪录主导。维护人进一步看到待办、贡献反馈、广告审核状态。
6. 三类板每板一个广告位，默认首屏外，维护人上传、系统审核，优质广告由系统提升。清楚标注广告，首屏提升不能挤掉方向、重要路况、主要打卡动作。后台显示草稿、待审、通过、驳回、位置、到期状态；维护人不能自行审核或提升。
7. 页面模块、接口、迁移及排期按本轮方向逐项对齐。模型须有独立山峰、具体点位、可复用有方向路段及三类板的稳定身份。弱网、权限、部署迁移和统计口径纳入路径验收。

## 招募状态

| 状态 | 展示与动作 |
| --- | --- |
| 尚无人维护 | 这座山，等一位山大王；查看职责与福利后申请 |
| 已有人维护 | 维护人、最近贡献；我也来帮忙 |
| 自己是维护人 | 按真实待办数量展示提示；进入维护台，无任务显示空态 |

认领不阻止其他熟悉此地的山友贡献。待办不能硬编码为“两条”；角色承担明确职责，广告福利不承诺收益。

## 首条路径验收

| 场景 | 通过条件 |
| --- | --- |
| 游客扫山顶码 | 首屏认出山名与海拔，可直接点“我到了”，无强制注册遮挡 |
| 生成纪念 | 凭证对应本次地点和时间；私人内容不自动公开 |
| 草稿后注册 | 返回原地点与原动作，记录和文字不丢失；公开发布仍由用户明确触发 |
| 重试与合并 | 弱网重试、重复点击、注册重试不重复生成到访；失败可重试，不能假报成功 |
| 多入口同山 | 两条线路及不同二维码进入同一山峰与山顶板，登顶路段数据分开 |
| 招募三态 | 游客、其他维护人、本人看到对应状态；已认领仍可帮助 |
| 维护工作 | 维护人可处理授权板的待办并看到贡献反馈；跨板操作被服务端拒绝 |
| 广告闭环 | 提交、审核、驳回重提、展示、到期可识别；审核与提升仅系统权限可操作 |
| 首屏布局 | 手机和桌面上方向、重要路况、打卡动作不被角色或广告遮挡 |
| 迁移与统计 | 旧二维码持续有效；历史留言和记录可追溯；扫码、到访、注册、留言分别统计，合并身份后去重 |

## 交付顺序

先盘点现有页面、接口与表结构，对照上述验收列出缺口；再落实稳定身份与游客记录合并契约，完成山顶路径的应用改造及验证。随后复用基础能力到岔路和路段，最后补齐首页聚合与个人关系视图。旧 W1–W6 仅作历史参考，不作为继续开发未来信、组队、照片流的依据。
