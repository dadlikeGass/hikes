## 4. 公开与私密

原则：**公开"到过哪个地点、哪天、用了多久"，其余不公开。**

| 内容 | 默认 |
| --- | --- |
| 昵称、地点名、到访日期（精确到日）、登顶用时、名次与百分位 | 公开 |
| 精确坐标与定位精度、打卡精确时刻、轨迹、邮箱、照片 | 私密，不进任何公开响应 |

上榜开关默认开；关闭等于完全退出榜与百分位统计（含分母）。只有注册账号可上榜，游客成绩当场可见并在此引导注册。

样本少于 8 时不显示名次与百分位，改显示"你是第 N 位完成者"。

上线前必须同步更新 `/privacy.html`。

## 5. 两类榜

### 登顶用时榜（占山为王页）

- 比较单元：「入口 → 山顶」这一对点位，**不是山峰，也不是完整线路**。不同入口长度与爬升不同，混排无意义。
- 展示：前三名用时 + 我的一行（用时 / 位次 / 百分位）
- 窗口：本周 / 本月 / 本年 / 有记录以来，一次请求返回全部

### 到访次序与人数榜（首页）

**我的理解**（需确认）：一个模块两组信息——

- 人数榜：本周到访人数最多的山头，取前若干，显示"本周 N 人"
- 次序榜：最近到访的时间线，每条含昵称、地点、相对时间、第几位到访

不含任何用时信息，与用时榜严格分开。人数与次序可以刷，用时不能，所以两者不能混在一个模块里。

### 打卡凭证（首页底部）

展示本人最近若干次到访凭证：地点、到访时间、第几位到访、本次用时（若有）。游客态显示本机游客的凭证。

## 6. 打卡

三种证据来源，服务端分级：

| 来源 | 判定 | `evidence_level` | 可入榜 |
| --- | --- | --- | --- |
| 扫码 | code 命中点位 | `code` | 是 |
| 定位 | 在点位半径内且精度达标 | `gps_close` | 是 |
| 定位或补传 | 精度差、距离远、时间可疑 | `gps_far` | 否 |

半径按点位类型分别设定，服务端校验；前端只上报原始坐标与精度。**具体阈值必须现场实测确定，不拍脑袋。**

离线：现场在本机落一条 `{occurred_at, code 或坐标, GPS 若 20 秒内可得}`，网络恢复后提交，服务端以 `occurred_at` 入账。两个必须处理的细节：

1. `visit_date` 取 `occurred_at` 的日期，不能用 `CURRENT_DATE`。否则周末爬山工作日补传会把日期、序号、"本周"统计一起算歪。
2. 序号按服务端入账顺序发放（避免离线补传插队），到访时间与排名用 `occurred_at`。

文案上不得承诺"没网也能打卡"：页面本身需要能被打开，无网可用的前提是页面已被缓存。

### 一个关键结论

**定位打卡让"起点打卡"不再需要实体码。** 用户在山脚打开页面用定位打卡即可，不必先在山脚贴一块码。这大幅降低用时榜的供给门槛——否则在有起点码之前，用时榜永远是空的。

配对规则相应放宽：**终点必须是扫码（强证据），起点允许定位。**

## 7. 未来信

只在「我」页加一个模块，不做通知、不做邮件、不做独立页面、不做分享。

解锁方式（需确认是否三种都要）：

| 模式 | 行为 |
| --- | --- |
| `date` 到期解锁 | 到设定日期后可看 |
| `checkin` 现场解锁 | 再次在该地点打卡时可看 |
| `open` 随时可看 | 相当于带地点标记的私人笔记 |

未到期的信只显示倒计时与写作地点，**任何接口与页面都不返回正文**。默认 5 年，可选 1 / 3 / 5 年。账号注销时随个人数据删除。

## 8. 工作包

按依赖排序，W1 是其余全部的前置。每包给出可执行的验收动作。

### W1 · 数据地基（纯增字段与一张新表，不碰任何页面）

- `visits` 增：`occurred_at`、`recorded_at`、`position_source`、`lat`、`lng`、`accuracy_m`、`evidence_level`、`client_uuid`
- `comments` 增：`observed_at`
- 新表 `segment_efforts`：`user_id`、`start_point_id`、`end_point_id`、`direction`、`start_visit_id`、`end_visit_id`、`start_at`、`end_at`、`duration_s`、`evidence_level`、`is_public`、`excluded_reason`、`created_at`；唯一键 `(user_id, start_point_id, end_point_id, start_at)`；索引 `(start_point_id, end_point_id, duration_s)`
- `letters`：`unlock_at` 改时间戳，增 `unlock_mode`、`status`
- 索引：`visits (point_id, occurred_at)`

验收：走 alembic；空库顺序升级通过；现有库升级后行数不变；回滚可行。

### W2 · 打卡闭环（服务端）

- 打卡接口支持 `scan` / `nearby` 两种来源、`client_uuid` 幂等、离线补传
- `GET /api/points/nearby`：按坐标查半径内点位，返回距离与建议半径
- 序号接口：四个窗口

验收：同一 `client_uuid` 提交两次只产生一条到访；跨日补传日期归属正确；序号按入账顺序；半径外打卡被拒并返回原因。

### W3 · 成绩配对与用时榜

- 终点打卡时由服务端配对并写入 `segment_efforts`
- 榜接口：一次返回四个窗口的样本量、前三、我的一行
- 反作弊：用时下限校验、同一天同一对只取最快、排除原因留痕

验收：不同入口的用时互不混排；样本 < 8 不显示名次与百分位；异常用时被拒且留原因；同一天只产生一条成绩。

### W4 · 首页：次序榜、人数榜、打卡凭证

- 前置：确认 §0 第 2 问与视觉形式
- 验收：游客可见；无数据时显示空态不编造；凭证与榜单不互相遮挡；榜查询失败不影响打卡入口。

### W5 · 占山为王页：用时榜

- 前置：确认该页位置与视觉形式
- 验收：前三名与"我的一行"齐全；未登录不显示"我的一行"而显示引导；无成绩时显示空态。

### W6 · 我页：未来信

- 验收：未到期的信在接口与页面上都不返回正文；到期后可打开；三种模式行为正确；注销后信件被删除。

## 10. 风险

| 风险 | 应对 |
| --- | --- |
| 用时榜因缺起点数据长期为空 | 定位打卡作为起点（§6），并提供空态文案说明缺什么 |
| 排名是零和的，必然有人刷 | 未注册不上榜、用时下限校验、同日只取最快、排除原因留痕 |
| 定位阈值拍脑袋会误判 | 先现场实测再定阈值，写进配置不上硬编码 |
| 离线时间被改 | 序号按服务端入账顺序；时间可疑的记录标 `gps_far` 不入榜 |
| 两套前端导致返工 | §0 第 1 问必须先回答 |
