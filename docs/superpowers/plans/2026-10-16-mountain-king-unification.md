# 统一山大王申请、山寨管理与路书封面开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 统一山大王申请，经平台审核授予权限，从留言版进入管理，并支持山寨协作及路书封面投稿。

**Architecture:** 山头是身份、审核互斥与成员关系的归属单位；点位和留言板关联山头。申请先存为私有申请记录，通过审核后才发布新山头并授予身份。沿用 FastAPI、PostgreSQL/PostGIS 与原生 JavaScript 前端，新增模块承载申请和山寨业务，避免继续扩大 app.js。

**Tech Stack:** 原生 JavaScript/CSS、FastAPI、SQLAlchemy SQL、PostgreSQL/PostGIS、Alembic、Docker Compose。

**Spec:** 本文件“已确认业务与页面结构”是本轮规格；依据用户在当前对话确认的统一申请设计。封面投稿方案为本轮建议，按独立工作包执行。

## 已确认业务与页面结构

### 入口与申请

占山为王页面：山头/岔路切换 → 参照首页主图尺寸的大卡片 → 我的申请进度 → 搜索筛选 → 榜单 → 山头列表。通过同一响应式尺寸规则实现卡片，不用一套固定高度适配所有屏幕；以首页当前 CSS 最终生效尺寸为参照，验收手机和桌面。

点击卡片打开独立申请页：
1. 搜索选择已有山头，或输入新山头；搜索覆盖服务端全部记录，显示地区、编号和现任负责人。
2. 已有山头展示已有资料；新山头填写名称、地区、准确位置、介绍和 GPX，海拔可由轨迹提取。
3. 两个必填文本框：“为什么想成为这个山头的页面版主？”（20–1000 字）；“作为山大王，你有什么经营计划？”（20–2000 字）。
4. 预计维护频率、昵称、可选联系方式；联系方式仅申请人和有权审核人员可见。
5. 保存草稿、提交申请；界面明确当前申请结果是负责人还是加入山寨。

新山头审核前不公开、不发可用二维码；审核通过后一次性创建山头、关联点位、留言板、短链与负责人。已有山头沿用原点位与二维码。现有自建点位直接发布接口必须关闭绕过路径，旧客户端得到明确升级提示。

新山头与现有山头相近时显示候选供确认；审核员可要求补充或关联已有山头，不能仅凭同名自动合并。申请由新建改为已有后若角色随之变化，需申请人确认。

### 申请状态

草稿 → 待审核 → 已通过 / 需补充 / 未通过；提交后允许撤回。需补充在原申请上修改、再次提交并保留版本。3 天是处理目标，超时标为延迟并提醒平台，不自动失效或通过。

没有负责人时申请成为山大王。多人申请由平台择一，其余申请进入“待确认加入”并通知用户；本人确认才转为加入申请，不能自动授予成员身份。

已有负责人且无山寨：记录加入意向，显示“等待山寨开放”；不承诺已经进入成员审核。山寨成立后邀请申请人确认继续。已有山寨：负责人提出接纳/拒绝意见，平台最终批准或驳回。负责人不能审核自己的申请。

### 留言版管理

留言版一级页面固定出现“我管理的留言版”；未获批用户看到空态和申请进度入口，获批后看到管理卡：山头、角色、待处理留言、申请提醒。

管理详情包括：概览、留言管理（全部/待处理/已隐藏）、山头资料与二维码、山寨管理、操作记录与设置。删除“线上版主”独立申请入口，旧入口重定向到统一申请。

山大王和山寨成员可发布路况、公告、置顶和有理由地隐藏留言；都不能改他人原文、打卡记录或查看私人信件。山大王可编辑介绍，成员提交修改建议。核心坐标、山头合并、负责人移交和成员移除由平台审批。广告仅负责人可提交素材，平台审核发布。所有权限由后端判定，前端隐藏按钮不能替代鉴权。

成员可退出；负责人移交需接任人确认和平台审核。无人接任则交回平台成为待认领，原留言、轨迹、二维码和打卡记录保留。山寨不另建留言板。组建山寨需名称、介绍、协作计划及招募要求，经平台审核。

现有主要文件：app/js/app.js（入口、路由、路书详情）、app/js/api.js（数据映射）、app/js/admin.js（维护台）、app/css/redesign.css、app/index.html、server/app/main.py、server/migrations/versions/、server/tests/。

建议新建：app/js/king-applications.js（申请及草稿）、app/js/clan-management.js（山寨页面）、server/app/king_service.py（状态迁移和事务）、server/app/king_routes.py（接口）、server/app/route_media.py（封面审核与存储适配）。按仓库实际依赖组织导入，不在新模块直接循环依赖 main.py。

数据：扩展维护申请以支持 existing/new 目标、申请原因、经营计划、私有新山头资料、版本号和状态；新增山头成员关系、山寨、成员申请、转让申请、操作记录和待发送通知。负责人唯一约束以山头 ID 为单位，不能以点位编号为单位。历史 claims 保留二维码和物料关联，不作为绕过新审核的授权入口。

拟定接口（实施时更新 OpenAPI）：
- GET /api/mountains/search?q=&cursor=：全库分页检索及管理状态。
- GET/PUT /api/me/king-application-drafts/{id}：账号私有草稿与乐观版本控制。
- POST /api/king-applications；GET /api/me/king-applications。
- POST /api/king-applications/{id}/withdraw、/resubmit、/confirm-join。
- GET /api/admin/king-applications；POST /api/admin/king-applications/{id}/review。
- GET /api/me/managed-boards；复用有鉴权的留言处理接口。
- POST /api/mountains/{id}/clan-applications；POST /api/clans/{id}/join-applications。
- POST /api/clan-join-applications/{id}/owner-opinion、/review。
- POST /api/mountains/{id}/transfer-applications；POST /api/transfers/{id}/accept、/review。
- POST /api/clans/{id}/leave；移除成员、交回平台均走可追溯审批。
- POST /api/routes/{slug}/cover-submissions；GET/POST 管理员封面审核接口。

旧 master-applications 接口采用适配或明确停用，不能与新接口产生两套权限。所有写接口验证状态、角色和资源归属；审批与通知写入同一事务的通知队列，避免授予成功但通知丢失。

## 回滚与实施约束

采用新增字段和新表优先的兼容迁移；切换前备份数据库并记录 Git revision。回滚优先回到兼容新数据的上一应用版本，不直接删除新表丢弃申请或成员记录。旧“直接创建并授权”接口不能随前端回滚重新开放。生产发布前必须验证兼容路径，必要时暂停新申请提交并保留读取。

普通用户照片上传需要持久化存储和后台审核能力；本机文件夹只用于开发，不作为生产存储方案。基础费用和存储供应商配置在部署前落实，不把缺少配置伪装为已上线。

## Review Focus

- 同一山头多个二维码及起终点必须共享身份边界。
- 申请等待期间的身份变化不能导致覆盖负责人或意外加入。
- 草稿、附件、联系方式与待审核照片不能被其他普通账号读取。
- 迁移后的历史身份不能被误提升权限，也不能无说明丢失权限。
- 图片、通知或弱网故障不能使申请出现半成功，或阻断轨迹和打卡核心路径。
