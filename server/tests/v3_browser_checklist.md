# V3 浏览器 / 真机人工核对清单

自动化能覆盖的部分已经写成 `v3_browser_drill.py`（Playwright + 隔离环境，8 个用例）。
下面这些**必须人来做**，因为涉及真机权限、真实网络与现场距离；没做就是没验收，
不要用本地模拟结果代替（计划 T3/T8 的通过标准明确写了这一点）。

记录方式：每条写清日期、环境、操作人、结果与截图路径，回填到 `docs/V3_ACCEPTANCE.md`
对应的编号里。

## A. 真机浏览器（HTTPS 域名，不是 localhost）

针对 iOS Safari、Android Chrome、微信内置浏览器各跑一遍：

- [ ] 扫码进入到达页 → 点「我到了」→ 出现「已到达：<地点>」凭证，序号说明是"该点位第 N 条到访记录"
- [ ] 首次进入时**拒绝**定位权限 → 点「附近定位打卡」→ 出现可读懂的提示，页面没有出现成功凭证
- [ ] 允许定位后 → 出现在半径内的点位列表（按距离排序）→ 选一个 → 打完卡 → 后端 `visits` 里 `evidence_level='gps_close'`
- [ ] 站在点位半径**外**（山顶 >100 m、其它点位 >150 m）→ 被拒绝，提示"距离点位较远"，`visits` 不增加
- [ ] 手机时间调快 10 分钟 → 打卡被拒绝并提示校准时间
- [ ] 飞行模式下打卡 → 提示"已保存在本机，待同步"；恢复网络 → 自动同步成功，`visits` 只增加一条
- [ ] 断网时关掉浏览器再打开、回到前台 → 队列仍在，且会重试
- [ ] 两个标签页同时打开 → 同时触发同步 → 只入库一条、同一序号
- [ ] 打开设备存储塞满（或浏览器禁掉 IndexedDB）→ 打卡失败时**不能**显示"已保存在本机"
- [ ] 在 A 账号下断网打卡 → 退出并登录 B 账号 → 队列**不会**自动传给 B；提示需要原来的身份

## B. 半径与坐标校准（必须到现场）

- [ ] 在试点点位实测：站在牌子旁打卡成功；走开约 120 m（山顶）/170 m（其它）打卡被拒
- [ ] 记录每次的 `distanceM` 与手机显示的 `accuracyM`，确认 100/150 m 的半径不会误伤站在牌子旁的人
- [ ] 把实测结论写回 `ascent_courses` / `points` 配置（必要时逐点覆盖半径）
- [ ] 现场采集试点路线的起点坐标（`server/seeds/v3_pilot_courses.json` 里的 `lat`/`lng`），
      跑 `--apply --coordinates-verified`，再验证扫码两端能配出成绩

## C. 页面观感（本地也可以先做一次）

- [ ] 390px：首页第一屏就能看到「扫码打卡 / 附近定位打卡」，不需要滚过长列表
- [ ] 1440px：首页、占山为王、山头详情、我、山间信箱五页都不断裂、不重叠
- [ ] 山头详情：选了山头之后才出现「登顶用时榜」次级模块；样本不足 8 人时只有解释，没有名次
- [ ] 山间信箱：封存中的信只显示状态与解锁条件（到期日 / 目标地点），页面上看不到正文
- [ ] 弱网：首页三块数据（山峰摘要 / 凭证 / 待同步）其中一块失败时，只有那一块显示重试

## D. 服务端作业

- [ ] 部署后确认 `v3-jobs` 在跑，且 `job_runs` 里能看到最近一次 `reconcile_efforts` 与
      `purge_visit_coordinates` 的 `status='ok'` 与时间（`docs/DEPLOY.md` 有查询命令）
- [ ] 到访满 30 天后，确认 `visits.location_geom` 与 `accuracy_m` 被清空、`evidence_level` 保留
